In-memory pub/sub decouples services for cross-cutting concerns. Publishers fire events, subscribers handle them asynchronously in goroutines.

## Usage

```go
// Publishing (returns nil; queue-full delivery is logged, not returned)
bus.Publish(ctx, eventbus.Event{
    Name:    events.ProductCreated,
    Payload: events.ProductEvent{ID: p.ID, Name: p.Name},
})

// Subscribing
bus.Subscribe(events.ProductCreated, func(ctx context.Context, event eventbus.Event) error {
    payload := event.Payload.(events.ProductEvent)
    // handle event
    return nil
})
```

## Event Bus Implementation

```go
type Bus interface {
    Publish(ctx context.Context, event Event) error
    Subscribe(eventName string, handler Handler)
}
```

- Handlers run on a **bounded worker pool** (16 workers, 1024-deep queue), so a burst of publishes cannot spawn unbounded goroutines
- Each job carries the publish call's context (falling back to `context.Background()` when nil)
- Queue full: the handler runs in a fresh goroutine and the overflow is logged
- Handler errors are logged, not retried — handlers should be idempotent
- In-memory only — events are lost on process restart
- No ordering guarantees across handlers
